## PPT SLIDE 2

설계 개요
상담사가 기다리는 30초 안에, 허용된 뷰만 읽기 전용으로 조회하는 검색기를 설계함

설계 대상과 범위

설계 대상  W-1 SQL 검색기(질문 → 정형쿼리 또는 NL2SQL → 결과 행 반환)
유저스토리  없음
시작 트리거  동기 요청(호출자가 검색을 요청하고 응답을 기다림) → 단계ID 접두어 S-R
설계 범위  요청 검증, 경로 판단, 계획 판정, SQL 검증, SQL 실행, 응답 반환, Groq LLM 커넥터
제외 범위  답변 문장 작성(호출자 몫), 뷰와 RLS 변경, 화면, 배포
DB 취급  시스템 내부 구성요소(사용자 결정). 외부시스템 연동과 커넥터 목록에서 제외

핵심 결정값

1
전체 시간 예산 30초, 종료 처리 시간 1초

2
LLM: Groq openai/gpt-oss-120b, 타임아웃 12초, 재시도 0회

3
SQL 검증 실패 시 다시 만들기 1회(반복 구간 L-1)

4
실행 계정 sql_retriever_user, 허용 뷰 7개, 결과 행 상한 200

5
필드 표기: 이름(타입, 필수 여부, 설명). 타입은 str, int, bool, date, list, obj

## PPT SLIDE 3

설계 개요: 처음 보는 분을 위한 용어 풀이
NL2SQL을 처음 접하는 검토자도 이 설계서를 읽을 수 있도록 용어를 한 줄씩 풀이함
용어 | 한 줄 풀이
NL2SQL | 사람의 말(자연어) 질문을 LLM이 SQL로 바꾸는 방식
정형쿼리 | 자주 묻는 조회를 미리 만들어 검증해 둔 고정 SQL. LLM은 ID만 고름
뷰(View) | 원본 테이블에서 필요한 컬럼과 기간만 골라 보여 주는 가상 테이블
행 수준 보안(RLS) | 같은 테이블이라도 세션에 지정한 회원의 행만 보이게 하는 DB 규칙
세션 변수 | 한 트랜잭션 동안만 DB에 알려 주는 값. 여기서는 회원ID, 기준일, 거래 제공 시작일
최악값 | 한 연동이 가장 오래 걸릴 때의 시간. 타임아웃 × (1 + 재시도 횟수)
남은 시간 예산 | 단계를 시작하기 전에 앞으로 쓸 수 있는 시간을 다시 재는 값
착지 단계 | 시간이나 재시도를 다 썼을 때 이어서 가는 안전한 단계

읽는 순서
① 흐름
② 단계
③ 연동
④ 반복
⑤ 합계
커넥터
⑥ 실행 중 시간 관리

## PPT SLIDE 5

① 단계 도출 및 순서 정의: 단계 목록과 흐름 유형
입력 워크플로우의 6단계를 그대로 쓰고, 분기 2곳과 반복 1곳을 둠

단계 목록
단계ID | 단계명 | 담당자 유형
S-R1 | 검색 요청 접수와 검증 | 규칙기반 코드
S-R2 | 정형쿼리 또는 NL2SQL 판단 | 생성형AI + 규칙기반 코드
S-R3 | 계획 적합성 판정 | 규칙기반 코드
S-R4 | SQL 검증 | 규칙기반 코드
S-R5 | SQL 실행 | 규칙기반 코드
S-R6 | 응답 구성과 반환 | 규칙기반 코드

흐름 유형
흐름 유형 | 위치 | 판단 이유
순차 | S-R1 → S-R2 → S-R3 → S-R4 → S-R5 → S-R6 | 앞 단계 출력이 뒤 단계 입력임
분기 | S-R3 | 계획이 "답할 수 없음"이면 SQL 없이 S-R6로 감
분기 | S-R4 | 통과는 S-R5, 실패는 다시 만들기 또는 오류 종료
반복 | L-1(S-R2 ~ S-R4) | 검증 실패 사유를 주고 SQL을 1회 다시 만듦
병렬 | 없음 | 모든 단계가 바로 앞 단계 출력을 써서 동시에 돌릴 단계가 없음

## PPT SLIDE 7

① 단계 도출 및 순서 정의: Mermaid 도식 스크립트
같은 흐름을 Mermaid 스크립트로도 남겨 누구나 다시 그릴 수 있게 함

flowchart LR
    T((동기 요청)) --> R1[S-R1 검색 요청 접수와 검증]
    R1 --> R2[S-R2 정형쿼리 또는 NL2SQL 판단]
    R2 --> R3{S-R3 계획 적합성 판정}
    R3 -- 답할 수 없음 --> R6[S-R6 응답 구성과 반환]
    R3 -- 검증 대상 --> R4{S-R4 SQL 검증}
    R4 -- 통과 --> R5[(S-R5 SQL 실행)]
    R4 -. 실패 1회차 L-1 .-> R2
    R4 -- 실패 2회차 --> E((오류 종료))
    R5 -- 성공 --> R6
    R5 -- 실패 --> E
    R1 -- 요청 오류 --> E
    R2 -- LLM 실패 대체 불가 --> E

보는 방법

1
mermaid.live/edit 접속

2
왼쪽 편집 창에 스크립트 붙여 넣기

3
오른쪽 위 전체보기 아이콘을 눌러 봄

노드 R1 ~ R6은 단계 S-R1 ~ S-R6, 점선은 반복 구간 L-1임

④ 반복 구간 명세
SQL 검증에 실패하면 실패 사유를 LLM에 주고 한 번만 다시 만듦
반복구간ID | 비즈니스 목표 | 단계ID | 재시도 | 최악값 | 착지 단계
L-1 | 검증을 통과할 때까지 SQL을 다시 만듦 | S-R2 ~ S-R4 | 1 | (12 + 0 + 0) × (1 + 1) = 24초 | 안전 종료(SQL_VALIDATION_FAILED 422)

대체 경로(키워드 매칭): LLM이 이미 nl2sql로 판단한 질문이라 맞지 않는 정형쿼리를 고를 위험이 있어 쓰지 않음

⑤ 워크플로우 명세
최악값 합계 24초로 전체 시간 예산 30초 안에 들고, 남는 5초는 DB와 규칙 처리 몫임
항목 | 값
워크플로우ID | W-1
이름 | SQL 검색기

종료 처리 시간 | 1초

## PPT SLIDE 20

⑥ 남은 시간 예산 정책: 측정과 계산
각 단계 시작 직전에 실제로 흐른 시간을 재고, 남은 시간 예산이 1.5초 이상일 때만 시작함
이름 | 계산식 또는 값
측정 시점 | S-R1 ~ S-R5 각 단계 시작 직전(S-R6는 종료 처리 시간으로 확보)
남은 시간 | 30 - 기존 사용 시간 - 1
남은 시간 예산 | 남은 시간 - SUM(앞으로 남은 단계의 외부 연동 최악값)
남은 외부 연동 최악값 | S-R2 전: 12초(반복 구간이라도 1회분) / S-R3 이후: 0초
시작 기준 시간 | 30 × 5% = 1.5초
DB 문장 제한 | statement_timeout = min(남은 시간 예산, 5초)

계산 예

예 1  S-R2 2회차 시작
사용 13초 → 남은 시간 30 - 13 - 1 = 16초
남은 시간 예산 16 - 12 = 4초 ≥ 1.5초 → 시작

예 2  S-R2 2회차 시작
사용 16초 → 남은 시간 30 - 16 - 1 = 13초
남은 시간 예산 13 - 12 = 1초 < 1.5초 → 착지(안전 종료)

예 3  S-R5 시작
사용 26초 → 남은 시간 30 - 26 - 1 = 3초
남은 시간 예산 3 - 0 = 3초 ≥ 1.5초 → 시작
statement_timeout = min(3초, 5초) = 3초

⑥ 남은 시간 예산 정책: 기준 미달 시 착지 단계
