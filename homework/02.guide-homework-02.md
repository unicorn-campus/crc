## 과제 설명
### SQL 검색기 설계
- 교육 시간에 작성한 SQL 검색기 설계서를 팀원 모두 이해 
- 예제 설계서(sql_retriever_워크플로우설계서.pptx) 기준으로 과제 설명
  - 워크플로우 단계 설계(페이지 5~7)
    - 워크플로우 단계와 흐름을 팀원 전체가 논의하여 결정 
    - 결정된 워크플로우를 mermaid script로 작성하고 확정
  - 각 단계별 설계(페이지 8~20)
    - 개인당 맡을 단계를 나눠 설계
    - 취합 후 다른 사람의 설계에 대해 피드백
    - 최종 단계별 설계 완성 
  - 반복 구간 명세(페이지 21)와 워크플로우 명세(페이지 22) 작성
    - 팀원 중 1명이 초안 작성
    - 다른 팀원과 리뷰하여 완료
  - 커넥터 설계(페이지 24 ~ 26)
    - 팀원 중 1명이 초안 작성: LLM 제공자는 groq으로 할 것을 권장
    - 다른 팀원과 리뷰하여 완료 
  - 남은 시간 예산 정책(페이지 27~28)
    - 팀원들이 함께 기준 항목값 정의: 종료 처리 시간, 시작 기준 시간
  - 논리뷰 추가 또는 수정(페이지 29)
    - 본인팀의 고객군에 필요하다고 생각되는 논리뷰를 추가 또는 기존 논리뷰를 수정
    - SQL은 'crc/rdb/init'폴더에 위치해야 함. Claude Code나 Codex에게 요청하여 작성
    - 논리뷰 수정 후 아래와 같이 db server를 완전히 내리면서서 볼륨을 삭제하고, 재시작해야 함
      DB서버 중지(-v 옵션으로 볼륨 삭제)  
      ```
      cd ~/workspace/crc/rdb
      docker compose down -v 
      ``` 
      DB서버 시작   
      ```
      docker compose up -d
      ```
  - 정형쿼리 추가 또는 수정(페이지 30)
    - 본인팀의 고객군에 필요하다고 생각되는 정형쿼리를 추가 또는 기존 정형쿼리 수정

- 작성된 설계서를 AI에게 검토요청: 아래 프롬프트를 적절히 수정하여 작업        
  논리뷰 수정 시 DB 재시작 후 수행해야 함   
  ※ '[입력]'섹션의 SQL검색기 설계서 경로와 '[예제]'섹션의 예제 SQL 검색기 설계서 경로는 반드시 변경해야 합니다.   

  ```
  [목표]
  {주제}: SQL 검색기
  {주제} 프로그램 개발을 위한 설계서 리뷰 
  [역할]
  클로니가 적절한 팀원과 협업하여 수행 
  [맥락]
  - 내 상황: SQL 검색기 설계서를 Human팀원과 작성한 후 AI 팀원들의 검토를 받아 최종 설계서를 작성해야 함
  - 독자: 설계에 참여한 Human 팀원, 개발자  
  [입력]
  - SQL검색기 설계서: {설계서 파일 경로 지정}
  - DB 접속 정보: 수행 중 사용자에게 받음. DB 종류, 호스트, 포트, DB 이름, 계정  
  - DB 비밀번호: `secrets/.env`의 `RDB_PASSWORD` 값  
  - View 생성 SQL 파일 경로: 수행 중 사용자에게 받음  
  - 설계 출력 기준 폴더(`{design_dir}`): 수행 중 사용자에게 받음
  - 설계 가이드: `references/design-workflow-connector.md` 
  - PPT 작성 가이드: `references/pptx-guide.md`  
  - 프롬프트 작성 가이드: `references/prompt-guide.md`

  [처리]
  - 사용자 입력 받기: DB 접속정보, View  생성 SQL 파일 경로, 출력 기준 폴더   
    - 설계 가이드, PPT 작성 가이드, 워크플로우, View 생성 SQL 파일을 끝까지 읽음  
    - View 생성 SQL 파일에서 아래 항목을 정리함  
      - 뷰 이름과 뷰마다 담는 내용(주석이 있으면 주석을 근거로 씀)  
      - 행 수준 보안(RLS), 세션 변수(예: `current_setting(...)`), 권한 부여(GRANT) 내용  
      - 뷰가 데이터를 보여 주기 위해 실행 전에 지정해야 하는 값(세션 변수, 기준일 등)  
    - DB 구조 읽기 스크립트를 만들어 실행함(다시 돌려도 같은 결과가 나오게 하기 위함)  
      - 접속 직후 세션을 읽기 전용으로 둠(PostgreSQL은 `SET default_transaction_read_only = on`)  
      - 계정 권한 확인: 관리자 권한(PostgreSQL은 `pg_roles`의 `rolsuper`, `rolcreaterole`, `rolcreatedb`,  
        `rolbypassrls`)이 하나라도 있으면 진행을 멈추고 사용자에게 알린 뒤 다른 계정을 받음  
      - 이 계정이 SELECT할 수 있는 뷰 목록, 뷰마다 컬럼 이름과 타입  
      - 원본 테이블에 대한 SELECT 권한 여부(NL2SQL 계정이 원본 테이블을 읽을 수 있으면 위험 항목으로 기록)  
      - 뷰마다 `SELECT * FROM {뷰} LIMIT 0`으로 접근 가능 여부만 확인함(데이터 행은 읽지 않음)  
      - 접속에 실패하면 오류 내용을 알리고 1단계 값을 다시 받음. 3회 실패하면 중단하고 보고함  
    - View 생성 SQL 파일의 뷰와 DB에서 실제로 보이는 뷰를 비교해, 한쪽에만 있는 뷰를 사용자에게 알림  
    - 출력파일: `read_views.py`, `db_catalog.json`  

  - SQL검색기 설계서 파악 및 이해

  - 설계 개선 사항 작성: 
    - 초안 작성
      - 사용자의 의사결정이 필요하면 요청하고 그 결과 기록: decisions.json
    - 관련 팀원 리뷰 
    - 최종안 작성: enhance_sql_retriever_design.md 
    - 사용자에게 검토 요청 및 승인 획득 
  
  - 개선된 설계서 작성: 
    - 설계서 스크립트: sql_retriever_설계서_v{N}.md
    - 설계서 PPT: sql_retriever_설계서_v{N}.pptx
  
  - 완료 보고 

  [출력]
  - DB 구조 읽기 스크립트: `{design_dir}/tools/read_views.py`  
  - DB 구조: `{design_dir}/work/db_catalog.json`  
  - 설계 결정 기록: `{design_dir}/work/decisions.json`  
  - 설계 개선 사항: {design_dir}/enhance_sql_retriever_design.md 
  - 설계서 스크립트: `{design_dir}/sql_retriever_설계서_v{N}.md`  
  - 개선된 설계서: {design_dir}/sql_retriever_설계서_v{N}.pptx
  - 톤앤매너: 설계서와 사용자 문의는 NL2SQL을 처음 접하는 사람도 알 수 있는 쉬운 한국어로 씀.  
  용어(NL2SQL, 정형쿼리, 최악값, 행 수준 보안 등)는 처음 나올 때 한 줄로 풀이함 

  [제약조건]
  - MUST:
    - 추가 정보나 내 의사결정이 필요하면 반드시 요청
    - 외부 정보 검색 시 공인된 사이트만 검색하고 출처를 반드시 설계서에 남김 
  - MUST NOT
    - 추축하여 작업하지 말고 원본 설계서, DB 구성 정보, 설계 가이드 등 입력정보에 기반하여 작업
  - 완료조건
    - 모든 출력물 생성 
  
  [예시]
  - 예제 SQL 검색기 설계서: {강사가 제공한 예제 SQL 검색기 설계서 경로 입력}
  ``` 

### SQL 검색기 개발
개발은 한 사람 PC에서 수행하고 팀 GIT Repo를 공유하여 실행 테스트 함     
- 소스 Base 디렉토리 결정: retriever/sql_retriever 권고  
- 프롬프트 'dev-sql-retriever.md' 수정 
  - '[입력]'섹션에서 설계서 스크립트와 설계서 PPT 경로 수정
- 프롬프트 'dev-sql-retriever.md' 수행하여 개발  
- 개발 완료 후 README.md를 읽어 가상환경 활성화 및 실행 
- Git Push 후 팀원들에게 Git Pull(최초에는 Git Clone)하도록 함 
  - AI툴 대화창에 'push'라고 입력하면 공통 지침(AGENTS.md)에 따라 commit 메시지 생성, .gitignore 생성 하여 푸시함  
  - 수동으로 push 하는 경우 AI툴에게 '.gitignore'파일 생성을 요청하여 위험한 파일(예: secrets/.env)이나    
    push가 불필요한 파일/디렉토리(예: .venv)가 업로드 안되도록 해야 함  
  - 다른 팀원들에게 'secrets/.env'파일을 메일이나 slack으로 안전하게 전달해야 함 

- 다른 팀원은 Git pull(최초에는 Git Clone) 후 'secrets/.env'파일과 내용 확인 후 README.md 지침에 따라 테스트 수행
